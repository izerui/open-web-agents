# 积分计费设计

本文是计费链路的交付设计,与代码一致。代码入口:`src/lib/modules/billing/`(受理、结算、清扫、对账)、
`src/lib/modules/run/`(运行与 worker)、`src/lib/modules/capabilities/domain/pricing.ts`(价目换算)。

## 1. 单位与价目

| 概念 | 规则 |
|---|---|
| 积分 | 用户看到的唯一单位。1 元 = 100 积分 |
| 微积分 | 内部记账单位,1 积分 = 1,000,000 微积分,全程整数(bigint),不丢精度 |
| 成本价 | 管理员添加模型时按「元 / 百万 token」录入:输入、输出、缓存读、缓存写四项 |
| 售价 | 成本价 × 100 × (1 + 加价比例),向上取整;按模型单独设加价。计费只用售价 |
| 价目版本 | 每次保存模型生成新版本。运行在受理时锁定版本,之后调价不影响已受理的运行 |

显示:金额 ≥ 0.01 保留两位小数,不足 0.01 显示「< 0.01」;余额向下取整;明细显示完整六位小数。

## 2. 谁付费

- 发起调用的账号付费:网页对话是登录用户,API Key 调用是签发 Key 的账号。市场里用别人的智能体,也是使用者付费。
- 余额按账号共用;每把 API Key 可设本月积分上限,账号也可设本月积分上限。
- 月度占用 = 冻结中的冻结额 + 已结算的实扣 + 已确认的欠额。按**受理月份**归属:一次运行受理时的冻结与之后每次追加都记在受理那个月。

## 3. 一次运行(智能体多轮循环)怎么计费

一次运行 = 用户发一次消息(或一次 API 调用、一次评测用例、一次 AI 设计),智能体在里面可能连续调用模型很多轮(思考 → 调工具 → 再调模型 …),直到输出结果。**按整次运行计费:受理时冻结,运行中按需追加,结束后按实际用量一次结清,多退少补。**

```
受理 ──► 运行中(多轮) ──► 结束 ──► 结算
冻结      每轮返回用量:       拿到最终费用   按锁定价目算出应扣
          接近冻结额就追加     (按模型的      冻结里扣,多的退回,
          追加不成且已超出     token 计量)    不够的补扣;补不上记欠款,
          → 停止运行                        充值后自动补扣
```

### 3.1 受理(与创建运行同一个数据库事务)
1. 解析本次要用的模型,锁定提供者与价目版本(主模型、子代理模型、别名槽)。
2. 锁住账户钱包行,算:可用余额、账号本月剩余、Key 本月剩余。
3. 冻结额 = min(主模型的单次冻结额〔默认 300 积分,可在模型里改〕, 可用余额, 账号剩余, Key 剩余)。
4. 可用余额低于 20 积分、或任一上限已满:拒绝发起,返回 402(`insufficient_balance` / `account_limit_exceeded` / `key_limit_exceeded`;
   升级遗留、还没按积分重新设置的旧美元上限为 `account_limit_pending`),什么都不留下。
   会话找不到可记账的账号(早期单用户时期留下的无归属会话)同样拒绝(`billing_account_missing`),不会免费运行。
5. 冻结、计费记录、运行记录一起提交;任一步失败整体回滚。同一幂等键重复提交拿回原任务,不重复冻结。
6. 受理时模型就不可用的,运行记为不可执行,执行时直接失败、不调用模型、不扣费。

### 3.2 运行中(多轮)
- 每次模型请求返回用量,按本次运行各模型里最贵的售价估一个上界。用到冻结额的八成就追加一份冻结(同样受余额与上限约束)。
- 追加不成、且已用超出冻结:这一轮请求返回后停止运行,结果为「积分不足,已停止」,按已产生的用量结算。
- 运行中不断写下累计用量快照(`runs.usage_snapshot`),供 worker 中途挂掉时兜底。

### 3.3 结束与结算
应扣 = Σ 各模型用量 × 锁定版本的售价(输入、输出、缓存读、缓存写分别计)。

| 情况 | 结算 |
|---|---|
| 正常结束 / 失败 / 取消 / 超时(拿到了用量) | 按实际用量结清。取消、失败也按已产生的用量计 |
| 用量里有认不出的模型或缺价目 | 那部分按本次运行**主模型**售价计,照常结清;对账报表里单列这部分 token |
| 部分消息没带模型名(如取消前收到的流式消息) | 这部分的输入、输出、缓存读、缓存写分开单独记下,按主模型售价计,与按模型的明细相加,结清 |
| 结算消息(result)没有按模型的明细 | 它给出的输入、输出、缓存读、缓存写四项分开记为未归属用量,按主模型售价(缓存按缓存价)计,结清;一轮里有多条 result 时逐条相加,带明细的那条之前的不重复计 |
| 结算消息的按模型明细里有不合规的项 | 模型名认不出(为空、过长且没有可用的规范名)但计数有效的:计数记为未归属用量,按主模型售价计,结清;某个计数读不出的(缺失、不是非负整数)另记「计量缺失」:读得出的照扣,这条保持暂记、不当成结清 |
| 结算消息的 usage、或按消息累计的用量里有计数读不出(负数、字符串等) | 同样记「计量缺失」:读得出的照扣,保持暂记。有效的 0、省略或为 null 的缓存项不算异常;同一条消息后来那份读得出就撤销 |
| 旧数据:只有总 token、既没有明细也没有未归属用量 | 总 token 按主模型售价计,结清 |
| 一条用量都没观察到 | 按 0 结清,冻结全部退回 |
| 冻结扣完还不够 | 另行补扣;余额不够补扣的记欠款,充值后清扫自动补扣一次 |
| 冻结没用完 | 多的退回可用余额 |
| 已扣多于修正后的应扣(费用能完整计价后) | 差额自动退回,记「多扣退还」流水 |
| worker 中途挂掉 | 先按用量快照暂记;24 小时内补到最终费用就按最终费用结清,否则按快照结清;连快照都没有按 0 结清 |

所有结算都由系统自动完成,不需要管理员处理。

### 3.4 可靠性(不漏收、不重复收)
- 实扣只按钱包里真正成功的扣款累计,不由预计费用倒推;补扣、退还都按编号幂等。
- 拿到最终费用后先写本机恢复文件,再写数据库,确认落库后才删;进程重启后自动补写。
- 用量快照带单调递增序号,晚到的旧快照不会覆盖新的。
- 时间比较一律在数据库里用运行表自己的时间与 `NOW()` 比,不受部署时区影响。

## 4. 积分来源

- 管理员人工发放(单个账号,或粘贴邮箱批量发放;按批次编号防重复)。
- 充值套餐:¥10 / 1000 积分,¥30 / 3090,¥100 / 10500,¥300 / 32400,积分不过期。目前由管理员确认订单入账,未接在线支付。
- 加价比例不高于充值赠送比例(8%)时,添加模型界面会提醒「可能没有成本余量或低于成本」。

## 5. 管理与复盘

- **积分管理页**:按邮箱批量发放、跨账号待核对列表(只读,系统自动补结算)、对账报表(按提供者、日期汇总 token、成本估算〔元〕、应扣、实际扣除;缺失数据只计条数,可导出 CSV),用于与上游账单核对。
- **提供者详情页「测试连接」**:上游回报的模型名与填写的模型标识不一致时直接提示,避免用量对不上模型。
- **用户积分页**:可用 / 冻结中、本月已用与上限、每次运行的应扣与实际扣除、流水。

## 6. 旧数据

早期版本有过「试算」(只记预计消耗、不扣款),已下线,计费恒为正式。试算留下的记录(`run_charges.mode = 'trial'`)
从没动过钱包:迁移 0054 清零其中未结清记录的冻结额,不占月度额度;运行结束后按旧记录结清,实扣 0。
