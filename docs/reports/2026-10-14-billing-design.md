# 账号算力与积分计费设计

状态:后续实施待办。本轮只设计计费,不实现充值、扣积分或套餐支付。

本文件描述 LLM 计费基础。新增多模态能力及逐次混合来源计费见
`2026-10-14-platform-roadmap.md`。最新决定是不支持 BYOK,所有模型能力由平台统一供给。
后续用 CapabilityCall 记录每次实际调用,不能只用整个 run 的一个总 token 数结算不同能力。

## 已确认规则

| 使用场景 | 模型凭证 | 向调用账号收费 |
| --- | --- | --- |
| 平台 AI 创建/编辑智能体 | 始终使用平台凭证 | 是,使用账号的平台积分或套餐额度 |
| 业务智能体运行(Web/API/嵌入) | 平台凭证 | 是 |
| 平台生图/生视频/语音等能力 | 平台凭证 | 是,按对应计量单位结算 |

所有入口不提供 BYOK 切换。历史用户模型 Key 不再读取,也不接受请求级 Key/网关覆盖。
计费归实际调用账号,不是由平台替用户承担费用。平台对外 API Key 仍用于集成方身份鉴权。
现有项目尚无积分钱包;先落实平台统一凭证并沿用账号级用量记录,再实现积分结算。

## 产品形态

账号是第一阶段的计费主体,不为计费先建设组织、子账号和多级分账体系。
以后有企业团队需求时再引入独立 billingAccountId,不把计费账户与文件隔离混为一谈。

用户设置中显示:
- 可用积分、预占积分、套餐剩余额度、有效期。
- 可用的平台模型能力及其积分价目。
- 充值与套餐、消耗明细、账单查询。
- AI 编辑与业务运行均明确使用平台算力。

管理员设置:
- 模型的成本单价与对用户的积分价格,分开维护。
- 可售套餐、价格、额度、有效期、允许模型及运行限制。
- 账号停用、补发或退回积分,每次调整记录原因。
- 平台成本、积分消耗和充值收入分别统计,不把三者当同一个数字。

## 资源与计价

模型调用的主要计量单位是 token,并非统一硬件算力单位。不承诺固定“一个积分等于多少 token”:
不同模型、输入/输出、缓存命中与缓存写入可能具有不同价格。

计价维度:
- 实际模型 ID,不是可能重新映射的 opus/sonnet 等别名。
- 输入、输出、缓存读取、缓存写入的数量,按供应商计量语义去重。
- 主代理与子代理的全部模型调用。
- 生效的价目版本与凭证来源。

建议采用整数积分子单位,避免浮点累计误差。示意公式:

    本次积分 = 各类 token 数量 × 对应积分单价之和

具体货币价格、积分兑换比例、毛利和套餐额度待平台经营者设定,本方案不预设数字。
供应商返回的美元成本用于成本核对,不能直接当成用户应扣积分。
模型网关不支持可靠用量时标为待核对,不把“拿不到成本”当成免费或臆测固定数额。

## 凭证来源与费用归属

每轮受理时明确记录:

    billingAccountId
    purpose: agent_run | agent_design | capability_call
    priceVersion
    effectiveModelId / alias
    credentialSource
    reservationId

后端根据入口确定用途和计价,不接受前端传入“免费”标记或供应商模型凭证。
平台缺少有效凭证时明确失败,不读取历史用户 Key,不接受用户指定的供应商 Base URL。

费用默认归调用账号:网页操作者,API Key 签发账号,嵌入 Token 对应的计费账号。
智能体作者不因别人调用其分享的智能体而自动承担费用。现有 billingUserId 可作为迁移起点。

## 扣费流程

1. 受理:鉴权、核对模式和模型价格、幂等检查。
2. 根据每轮消费上限预占积分,余额不足则不入队。
3. 执行:携带本轮固定的计费上下文,累计实际用量。
4. 接近限额:拒绝继续扩大消费或停止后续调用。停止有延迟,预占要留缓冲,
   不能承诺供应商调用中的 token 能精确卡在某个余额上。
5. 结算:按实际可信用量扣除,释放未消费的预占。
6. 用量不确定:保持待核对状态和适度的资金预留,按有记录的策略处理,
   不能直接退还全部预占后重跑导致免费消费。

钱包预占必须原子,解决同一账号并行启动多次运行同时花同一份余额的问题。
业务运行终态与账务结算状态分开:任务失败或取消不代表没有 token 消耗。
每条结算具有唯一幂等键,重复终态事件、worker 重启或支付回调都不得重复扣款。
退费通过反向流水实现,不删除或改写历史扣费流水。
不自动重试可能产生外部副作用的业务运行来修复账务问题。

## 套餐

先做两种简单产品:
- 积分充值包:一次购买固定积分,有效期明确。
- 周期套餐:固定周期发放额度,限制模型与并发,续期规则明确。

明确展示额度何时生效、是否结转、到期处理、扣减顺序和超额行为。
建议先到期的套餐额度优先使用,再用长期充值余额;默认余额不足即停,
不默认开信用透支或自动扣银行卡。
第一版不要做无限量套餐、复杂优惠叠加和多级分销。
AI 编辑与业务平台调用共用钱包,账单中按用途分开;价格可以独立配置。
账号同时受并发、运行时长和存储限制,不能把 token 套餐误解为无限平台资源。

## 最小数据模型

- 账号钱包:余额与预占,有原子更新控制。
- 账务流水:充值、套餐发放、消费、释放、退回、人工调整,只追加。
- 算力价目:实际模型、计量维度、价格版本与生效时间。
- 套餐与权益:套餐定义、账号购买的有效额度及有效期。
- 充值订单:金额、币种、支付状态、幂等标识,支付方确认后才到账。
- 运行计费记录:凭证来源、价目快照、用量、预占和结算状态,关联现有 run。

优先复用 MySQL 事务和现有 worker,不单独建设账务微服务或新队列。
钱包流水为资金事实,usage 页面是统计展示,不能从可能不完整的聚合统计反推余额。
